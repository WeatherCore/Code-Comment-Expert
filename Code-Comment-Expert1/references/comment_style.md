# 注释规范：意图级（Intent-Level）

注释回答的不是「代码做了什么」（那读代码就知道），而是「**为什么存在 / 解决什么业务问题 / 有什么约束与坑**」。

## 一、各语言落点

### Java（Javadoc，`/** ... */`，置于类/方法上方）
```java
/**
 * 订单状态机：管理下单→支付→发货→完成的生命周期。
 * 关键约束：仅支付成功可流转到「已发货」，重复发货会被幂等拦截（见 #dedupe）。
 * 注意：状态变更必须走本类，禁止业务方直接 update 订单表。
 */
public class OrderStateMachine { ... }
```

### Python（docstring，`""" ... """`，置于类/函数下方或上方）
```python
class OrderStateMachine:
    """订单状态机：管理下单→支付→发货→完成的生命周期。

    关键约束：仅支付成功可流转到「已发货」，重复发货走幂等拦截。
    为什么单独抽类：历史上是散落在 Service 里的 if-else，漏判导致超发，
    故收敛为单一可信入口。
    """
```

### 前端（JS/TS，块注释 `/** */` 或行注释 `//`，v1 仅基础支持）
```ts
/**
 * 下单按钮的提交处理器：组装购物车快照并调用 createOrder。
 * 注意：提交前本地校验库存仅为体验优化，最终以服务端校验为准。
 */
```

## 二、意图级写法清单（每条注释尽量含其一）
- **业务背景**：这段逻辑对应哪个真实业务环节。
- **关键约束 / 不变量**：什么情况下不能越界（如幂等、事务边界）。
- **设计动机**：为什么这样写而不是别的（历史坑、性能、合规）。
- **调用约定**：谁来调、返回什么语义、异常代表什么。
- **坑点预警**：容易误用的地方。

## 三、反例（禁止产出）
```java
// 设置订单状态        ← 流水账，复述代码，删除
int a = b + 1; // 加一   ← 无意义，删除
/**
 * @param order 订单   ← 纯 @param 无叙述，不算意图级，仅当无其他可写时保留
 */
```

## 四、不覆盖已有有效注释
- 若类/方法上方已有**非占位** doc-comment（有叙述、非 `@Generated`、非空、非纯签名罗列），保留不动。
- 仅在「缺失」或「仅有占位/生成标记」时补写意图级注释。
- 测试、配置、静态资源、构建产物文件整体跳过，不注。

## 五、不确定就标「待确认」
遇到读不懂的代码，**不要编造业务意图**，写：
```
// 待确认：此处逻辑疑似处理 X，但未找到对应业务文档，需与负责人核实。
```
